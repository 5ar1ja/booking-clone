## 2. Критерии оценки

### 2.1 Техническая часть (25 баллов)
[cite_start]Техническая часть должна включать все наработки за семестр, включая исправления ошибок по предыдущим комментариям[cite: 19, 20].

**Основные требования:**
* **Архитектура и стандарты:**
    * [cite_start]Наличие **ER-диаграммы** моделей Django[cite: 21].
    * [cite_start]Структура проекта должна строго соответствовать лекционной (папки `apps`, `settings`, `env`, `base` и т.д.)[cite: 23].
    * [cite_start]Полное соответствие стандарту **PEP8** и использование **типизации**[cite: 25].
    * [cite_start]Минимизация дублирования кода через декораторы и миксины[cite: 42].
* **Модели и пользователи:**
    * [cite_start]Полная конфигурация всех моделей[cite: 24].
    * [cite_start]Реализация **кастомной модели пользователя** (Custom User Model)[cite: 27].
    * [cite_start]Авторизация через **JWT**[cite: 27].
* **API и документация:**
    * [cite_start]Полная документация в **Swagger и Redoc** (схемы запросов/ответов, все HTTP-коды, примеры, параметры и права доступа)[cite: 28].
    * [cite_start]Индивидуальные сериализаторы для GET и POST запросов (запрещено использовать один и тот же)[cite: 29, 30].
    * [cite_start]Настройка фильтрации для GET-запросов[cite: 30].
    * [cite_start]Оптимизация сложных полей (M2M, Foreign Key, `annotate`)[cite: 31].
* **Тестирование и автоматизация:**
    * [cite_start]**Unit-тесты:** Для каждого эндпоинта необходимо 3 теста (1 успешный кейс и 2 негативных)[cite: 34, 35].
    * [cite_start]**Management commands:** Команды для полного заполнения базы данных[cite: 36].
    * [cite_start]**Shell-скрипты:** Автоматизация запуска проекта, создания админа, проверки переменных окружения и т.д.[cite: 40, 41].
* **Продвинутые технологии:**
    * [cite_start]**Celery:** Минимум одна отложенная (delayed) и одна периодическая задача[cite: 37].
    * [cite_start]**Docker:** Настройка `docker-compose` для всего проекта (БД, Redis и др.)[cite: 38].
    * [cite_start]**Redis:** Использование для rate limiting, выбора языка или OTP[cite: 43].
    * [cite_start]**WebSockets или SSE:** Реализация хотя бы одного из этих протоколов[cite: 44].
    * [cite_start]**Асинхронность:** Наличие асинхронного кода для I/O bound задач[cite: 45].
    * [cite_start]**Логирование:** Сконфигурированное логирование по всему проекту, включая хранение в файлах[cite: 46].
    * [cite_start]**Локализация:** Поддержка i18n для всей системы[cite: 39].
* **Управление проектом:**
    * [cite_start]Использование **Actarum** (actarum.com) для управления задачами (эпики, спринты, запись экрана)[cite: 32].
    * [cite_start]Тимлид должен распределять задачи и управлять разработчиками[cite: 33].

Этот текст представляет собой список заметок (ревью кода или план разработки) по Django-проекту и процессам в GitHub. Ниже представлена структурированная версия в формате Markdown.

Заметки по ревью кода и архитектуре Django
1. Django & URLs (Middleware/Settings)
Скрытие локальных адресов: Заменить 127.0.0.1 в URL-адресах на переменные окружения или абстрактные имена, чтобы не хардкодить локальные пути.

Конфигурация (conf): * При ошибках в конфиге приложение должно «падать» сразу.

Принцип Fail-fast: лучше, чтобы проект сломался в момент запуска (на старте), чем работал некорректно в процессе.

Очистка кода: Убрать лишние синонимы и дублирующие по смыслу переменные.

DEBUG: Убедиться, что режим DEBUG корректно прописан для local и production сред (использовать переменные окружения).

2. GitHub & Workflow (Процесс разработки)
Pull Requests: Все изменения вносятся строго через PR.

Main Branch: Прямой пуш (push) в ветку main должен быть закрыт.

Code Review: Обязательная проверка кода перед слиянием.

3. Custom User & Модели
Личные комментарии: Проверить, что именно возвращает модель/метод.

Масштабирование: Разделить пользователей на роли для удобства будущего расширения системы.

Логика Tenant (Rentor/Landlord):

Переписать логику взаимодействия в моделях.

Использовать исключающее ИЛИ (XOR) для определения ролей.

Избегать лишних импортов (особенно внутри models.py, где это возможно).

4. Качество кода (Clean Code)
Магические числа: Запрещено использовать «голые числа».

Константы: * Все важные значения выносить в константы.

Объявлять константы внутри классов для повышения переиспользуемости.

Это формирует хорошие привычки: когда логика изменится, поправить значение в одном месте будет проще.

DRY (Don't Repeat Yourself): Убрать дублирование в сериализаторах («масло масляное»).

5. Reviews & Frontend (API)
ID в списках: Обязательно передавать ID объектов в списках отзывов (Reviews).

DOM Tree: Фронтенду (DOM-дереву) для оптимальной отрисовки нужны уникальные ключи (key).

Оптимизация: Чтобы фронтенд рендерил данные корректно и быстро, бэкенд должен всегда отдавать уникальный ID.

Swagger: Использовать относительные (relative) пути.

Авторство: Проверить корректность передачи данных об авторе.

6. Serializers (Сериализаторы)
Разделение: Не рекомендуется использовать один и тот же сериализатор для разных задач.

Количество: «Дофига сериализаторов — это не плохо». Лучше сделать много маленьких и специфичных, чем один перегруженный.

JWT: Использовать для аутентификации.

7. Viewsets & Views
ModelViewSet: Не злоупотреблять автоматизацией, если логика сложная.

Документирование: Обязательно писать Docstrings и комментарии к сложным участкам.

Обучение: В процессе обучения лучше использовать APIView, чтобы понимать, как работают методы (GET, POST и т.д.), прежде чем переходить к автоматическим ViewSets.
